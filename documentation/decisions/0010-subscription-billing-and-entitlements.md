# ADR 0010: Subscription billing and entitlements

Status: accepted for test-mode rollout (2026-11-03). Prices, trial length, grace period and annual discount are commercial assumptions (ASSUMPTIONS #67-77) and must be validated with customers before general release.

## Context
BSM monetizes through subscriptions: facilities and agencies pay, professionals never do. The repository already had a different billing feature: **manual placement-fee invoicing** (migration 0010, `/admin/billing/*`, `/organizations/:orgId/billing/invoices`) in which staff invoice a percentage of approved timesheet pay and record payment received outside the platform. That feature is unchanged and remains independent. There was no payment-provider integration, no plan model and no feature gating. No Stripe SDK was installed.

## Decision
1. **Stripe is the system of record for payments; the database holds a projection.** `organization_subscriptions` (one row per organization) is written only from provider data: webhook events, or the provider's response to a cancel/resume call our server made. Nothing in a browser request body sets subscription state, plan, price or organization. The success redirect after checkout proves nothing; the UI waits for the server to report the subscription.
2. **Adapter, no SDK.** `integrations/billing.ts` defines `BillingProvider` and a `fetch`-based Stripe implementation (form encoding, idempotency keys, HMAC signature verification with a 5-minute tolerance). Unconfigured (`STRIPE_SECRET_KEY`/`STRIPE_WEBHOOK_SECRET` unset) means 503, never a simulated success. This follows AGENTS.md ("never fake payments or integrations") and avoids a new dependency.
3. **Catalog in the database.** `subscription_plans` (one row per plan and billing interval, price in integer cents), `plan_entitlements` (key, type, JSON value; `null` for an integer means unlimited). Seed rows are ordinary data. Price, interval and Stripe price are frozen once any customer is on the plan; create a new plan instead. A plan is purchasable only if active, public and attached to a Stripe price.
4. **Entitlements are decided on the server, per request.** `getOrganizationEntitlements` combines the organization's `billing_mode`, the subscription and the plan. `decideAccess` is a pure function: active/trialing allow; past-due allows only until `grace_period_end` (set once from the first failure, default 7 days, `BILLING_GRACE_DAYS`); cancel-at-period-end keeps access to the exact end date; unpaid, canceled, paused, incomplete and none deny; a period more than 3 days lapsed counts as expired so a late renewal webhook does not lock out a payer.
5. **Rollout is gated twice.** `BILLING_SUBSCRIPTIONS_ENABLED=false` (default) turns off checkout and all gating. Even when on, an organization is `exempt` (default, behaves exactly as before) until a super-admin-class staff member with MFA sets it to `enforced` (audited). Nobody is made to pay automatically.
6. **Enforcement points are route-level only.** Added middleware on: talent search (enabled + monthly allowance), match-run creation (`matching.enabled`), location create and re-activation (`active_locations.limit`), facility and agency analytics, agency submissions (monthly allowance) and roster invitations (`agency_roster.limit`). Files under `modules/matching/` that hold eligibility, ranking and weights are untouched.
7. **Atomic usage.** One `INSERT ... ON CONFLICT DO UPDATE ... WHERE quantity + n <= limit` statement reserves usage, so concurrent requests queue on the row lock and cannot overshoot. A reservation is returned if the response ends in an error status. Count-based limits (locations) lock the organization row while counting and inserting. The roster limit is a plain count check (not atomic): a small overshoot under a race is accepted.
8. **Webhooks.** The route is mounted before `express.json` with a raw-body parser. Order: verify signature, record the event id (unique), dispatch, record the outcome. Duplicates return 200 without reprocessing; a failed event stays `failed` and is reprocessed on redelivery; permanent mismatches (metadata names a different organization than the customer belongs to) are recorded and acknowledged so Stripe stops retrying. The organization always comes from our own customer mapping, never from payload metadata alone. Events older than the newest applied one for that subscription are ignored (`last_event_created`). A second live subscription for an organization is refused and flagged (`duplicate_subscription`) for a person to resolve. Payloads are never stored or logged: `billing_events` keeps ids, type, outcome, attempt count, an error code, and the invoice amount.
9. **Plan changes go through the Stripe Customer Portal.** Checkout is for the first subscription; switching plans, updating cards and viewing receipts happen in the hosted portal, and the change arrives by webhook. This avoids building proration logic and keeps card data out of scope.
10. **Discounts** are Stripe coupons (single redemption) created by an audited staff action (`billing_adjustments`), applied at that organization's next checkout, marked consumed when a subscription carries the coupon. Percentages above 50 need a super admin.
11. **Permissions.** New org permission `billing.manage` (organization owners only) for checkout, portal, cancel and resume. Reading uses the existing `billing.read` (owner, finance); the entitlements and usage endpoints use `org.read` so any member can see what the plan allows. Staff use the existing `admin.billing_manage` (super admin, finance admin) with MFA.

## Route naming
The existing `/organizations/:orgId/billing/invoices` serves placement-fee invoices, so Stripe charges are at `/billing/subscription-invoices` (read live from Stripe, nothing copied). `/billing/plans` is public (active public plans, no provider ids).

## Consequences
- Metrics (MRR, ARR, churn, conversion, failed-payment rate, gross revenue) are computed from the projection and the webhook ledger with published definitions (`GET /admin/billing/metrics`). MRR is before coupons. Refunds and credits are not tracked yet.
- Stripe dashboard changes to a subscription reach us only through webhooks; staff can re-sync one organization on demand.
- The AI assistant reads analytics through its own tools, not the analytics route, so it is not gated by `workforce_analytics.enabled` (ASSUMPTIONS #78).

## Alternatives rejected
- Trusting `checkout.session.completed` or the redirect: rejected (spec and security).
- Storing webhook payloads for replay: rejected (payment data minimization); re-sync reads from Stripe.
- A stored per-organization entitlement override table: deferred; custom contracts use a private plan.
- Gating by deleting data or blocking login on non-payment: rejected; only paid features stop.
